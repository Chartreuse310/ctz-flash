# 图谱动画卡顿诊断

> 模态窗口右侧的「图谱」在缩放 / 拖拽 / hover 时卡顿。本文记录诊断过程与定案修法，结论是**砍掉自研的"每帧重写 DataSet"机制**，让 vis-network 走原生渲染路径。

## 现象

- 触控板双指缩放图谱时明显掉帧、不跟手
- hover / blur 节点时有肉眼可见的小顿挫
- 模态刚打开瞬间，物理模拟有一段"抖动归位"

## 根因

**最大的元凶：`applyScale` 在每一帧都重写整个 DataSet。**

这套机制是为了实现"缩放时节点屏幕大小恒定"这个特效而写的。`assets/garden.js` 的 zoom 处理每帧调用 `applyScale`：

```js
network.on('zoom', (params) => {
  ...
  scaleFrame = requestAnimationFrame(() => {
    applyScale(params.scale);   // ← 每帧调用
  });
});
```

而 `applyScale` 每一帧做的事：

- `visNodes.update(...)` —— 给**所有节点**重写 `size` + `color` + **`font`**（含 `size` / `face` / `vadjust`）
- `visEdges.update(...)` —— 给**所有边**重写 `width`

问题在于：

- 改 `font` 字段会强制 vis-network 重新 `measureText` 测量标签、重算节点包围盒——**最贵的操作**
- 改 `color` 会触发整屏重绘

于是连续手势（≈60fps）期间，每一帧都在做「全量 DataSet 更新 + 标签重测 + 全量重绘」，与 vis-network 自身的 canvas 缩放重绘抢帧 → 掉帧。

### 两个次要叠加因素

1. **hover / blur 也调用 `applyScale`** —— 为了高亮**一个**节点，重写了**所有**节点的数据，每次悬停 / 移开都有一个明显顿挫。
2. **超出范围时 `network.moveTo({ scale: s })`** —— 缩放到 0.5 / 3 的钳位边界后，每帧强行 `moveTo` 反向修正 scale，与正在进行的捏合手势"打架"，边界处出现抖动。
3.（次要）`stabilization: { iterations: 100 }` 让模态打开瞬间有可见的"抖动归位"。

## 与 Obsidian 的差距

Obsidian 的图谱缩放时，节点**随缩放自然变大变小**（力导向图谱的正常手感），并不试图保持"屏幕恒定大小"。当前这套反比缩放 + 每帧重写数据的写法，是为了实现一个 Obsidian 本身没有的特效，代价就是卡顿。

## 定案修法

把"每帧重写 DataSet"这套机制整个拿掉，改走原生路径：

1. **删除 zoom 里的 `applyScale` 调用与整个 `applyScale` 函数**，节点随缩放自然缩放（对齐 Obsidian 手感，且零额外开销）。
2. **hover 只更新被悬停的那一个节点**（`visNodes.update({ id, size, color, font })` 单条），而不是全量。
3. **删除 zoom 里的 scale 钳位 `moveTo`**，改用 vis-network 自带的 `interaction.zoomView` 范围限制（或保留钳位但用 `setOptions` 一次性设范围，而非每帧修正）。
4. **物理稳定**用 `stabilization: false` 配合自然衰减，或调小迭代次数，避免打开时的抖动。

改完缩放 / 拖拽 / hover 都只走 vis-network 原生渲染，流畅度接近 Obsidian。改动集中在 `renderGraph` 一个函数内。
